eth0: a whole packet sensor on one ESP32-S3

NET-001 · Testing 2026-10-19 ESP32-S3 W5500 PCAP Web Serial

eth0 started as a simple question: how much of a real network sensor can you fit on a $25 board with a wired NIC and an SD card, and drive the whole thing from a browser with nothing to install? The answer turned out to be most of it.

Everything here is for networks you own or are explicitly authorised to monitor. eth0 is a lab and home-lab tool.

What it is

A Waveshare ESP32-S3-ETH sits on a wired segment and captures raw Ethernet off a W5500 in MACRAW mode, writing standard PCAP to an SD card. On top of the capture path it runs an IDS rule engine with an alert ring, passive network discovery (ARP/STP/LLDP/CDP/mDNS/NBNS), and — using the S3’s own radio — Wi-Fi and BLE scanning with a learned WIDS baseline. You talk to it from a single-file web console over the Web Serial API: no backend, no app, just a browser tab and a USB cable.

The canonical runtime and UI name is eth0; the repository folder is eth1, a naming scar I’ve decided to keep rather than rewrite history over.

How the pieces fit

The firmware is deliberately split into focused translation units instead of one heroic .ino:

ModuleResponsibility
net_coreW5500 MACRAW capture, Ethernet init, DHCP with static fallback
securityIDS rule engine, alert ring, blocking/blacklist state, WIDS
protocolsARP/STP/LLDP/CDP/mDNS/NBNS parsing, host and neighbor tables
wirelessWi-Fi and BLE scanning, WIDS baseline learning
clihuman serial menu plus the machine-readable Web Serial JSON bridge

Boot order is boring on purpose: status LED, both SPI buses, SD card, Ethernet (DHCP first, static fallback), then socket 0 is reopened as MACRAW with the MAC filter disabled so capture is promiscuous. From there every frame fans out to three consumers — the PCAP writer, the stats/IDS path, and a small ring buffer the browser polls for its live packet view.

The design calls that actually mattered

Two SPI buses, not one. Sharing a bus between the W5500 and the SD card causes contention — capture stalls while SD writes land, and you lose frames. Ethernet gets SPI2/FSPI, the SD card gets SPI3/HSPI. That one decision removed a whole class of intermittent errors (the GPIO pull-up and cold-boot clocking details are their own note).

The serial protocol is a contract. The browser console is tightly coupled to exact command strings and response shapes, so a casual firmware tweak can silently break the UI. I treat the JSON bridge as a documented, versioned protocol and keep a UI-to-firmware command matrix in the repo so drift is visible instead of surprising.

Persist the operator’s context, not the attacks. Alerts, module toggles, IDS rules, the WIDS baseline and an append-only audit trail all snapshot to /state/ on SD and reload on boot, so a power blip comes back where you left off. Offensive actions are deliberately not auto-resumed after a reset — the device wakes up observing, never acting.

Where it’s rough

I’d rather name these than pretend they aren’t there:

  • Throughput is bounded by the W5500 and SPI, not line rate — this is a segment sensor, not a backbone tap.
  • The UI currently exposes more than purely defensive workflows; capability-gating the higher-risk controls behind an explicit safe-mode is the next real piece of work.
  • The firmware began life as a monolith and is being broken into the modules above incrementally, not all at once.

Where it’s going

The near-term backlog is all about making it safer and more maintainable rather than adding capability: the documented/versioned protocol, the command matrix, safe-mode gating, and a host-side replay harness so the browser UI can be exercised against recorded serial traffic with no hardware attached.
